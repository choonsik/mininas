# MiniNAS 동영상 무손실(원본 화질 유지) 스트리밍 버퍼링 최적화 검토 보고서

**작성 일자**: 2026-11-16  
**대상 시스템**: MiniNAS (Go 백엔드 + React 프론트엔드)  
**핵심 요구사항**: **"화질을 낮추지 않고(100% 원본 유지), 네트워크 상태에 따른 멈춤(버퍼링) 현상 개선"**

---

## 1. 현황 및 문제 원인 분석

### 1.1 현재 스트리밍 아키텍처
* **백엔드**: `/api/files/stream` 엔드포인트에서 Go의 `http.ServeContent`를 사용하여 파일에 대한 HTTP Range Request(206 Partial Content) 직접 서빙.
* **프론트엔드**: `MediaViewer.tsx`에서 순수 HTML5 `<video src="/api/files/stream?..." controls>` 엘리먼트로 직접 재생.

### 1.2 네트워크 환경에 따른 멈춤(Stuttering) 발생 원인
1. **원본 비트레이트 직송출**: 고화질 영상(FHD 1080p, 4K 등)은 초당 전송량(10Mbps~50Mbps 이상)이 큼. Wi-Fi 감도 저하, 음영 지역, 원격 외부 접속 시 대역폭이 비트레이트보다 떨어지는 순간 버퍼 고갈 발생.
2. **브라우저의 소극적 기본 버퍼 정책**: 크롬/사파리 등의 `<video>` 태그는 데이터와 메모리 절약을 위해 **앞으로 약 3~10초 분량만 최소한으로 선행 다운로드**함.
3. **버퍼 채터링 (Buffer Chattering)**: 버퍼가 고갈되어 멈춘 후, 0.5~1초치만 채워져도 즉시 재생을 시도하다가 다시 멈추는 "재생-멈춤 반복" 스트레스 유발.
4. **일시정지(Pause) 시 다운로드 중단**: 최신 브라우저는 일시정지 버튼을 누르면 대역폭 절약을 위해 다운로드 연결 자체를 중단하거나 최소화하여, 사용자가 '미리 받아두기'를 할 수 없음.

## 2. 핵심 엔지니어링 개념: 버퍼링의 역설

> **"속도가 느리면 많이 쌓고, 속도가 빠르면 적게 쌓아야 하는 것 아닌가?"**

사용자의 직관적 희망사항과 실제 시스템 엔지니어링 사이에는 물리적 한계로 인한 역설이 존재함:

| 구분 | 느린 네트워크 (수도꼭지 졸졸) | 빠른 네트워크 (소방 호스 콸콸) |
| :--- | :--- | :--- |
| **사용자의 직관 (희망사항)** | 끊길 위험이 높으니 5분~10분치를 넉넉히 받아두고 싶음 | 실시간으로 잘 들어오니 조금만 받아도 괜찮음 |
| **실제 물리적 한계** | • 소비 속도(재생) > 유입 속도(다운로드)<br>• 5분치를 모으려면 10분 이상 **로딩 바(스핀)만 대기**해야 함<br>• 재생 시작 시 버퍼를 **물리적으로 많이 쌓을 수가 없음** | • 5분치 버퍼를 **단 3~5초 만에 채울 수 있는 능력**이 있음<br>• 순식간에 가득 채워두면 향후 네트워크가 완전히 끊겨도 5분간 무중단 재생 보장 |
| **엔지니어링 전략** | • **최소 안전 버퍼(10~30초)** 확보 시 즉시 재생 시작<br>• 사용자가 원할 때 **일시정지(Pause) 중 백그라운드 프리페치** 허용 | • **동적 하이브리드 버퍼 확장(3~5분)**으로 여유 대역폭 완전 활용<br>• 메모리 상한선(200~300MB)으로 브라우저 탭 보호 |

## 3. 화질 무손실 최적화 솔루션 4단계

### 솔루션 1: 일시정지(Pause) 중 백그라운드 프리페치 (Pause-Buffering)
* **내용**: 사용자가 영상을 일시정지 상태로 두더라도 백그라운드에서 다음 청크들을 지속적으로 요청하여 버퍼를 가득 채움.
* **효과**: 네트워크가 느린 원격 환경에서도 감상 전 1~2분 정도 잠시 멈춰두면, 원본 화질 손실 없이 끊김 없는 연속 시청 가능.

### 솔루션 2: 타임라인 버퍼 캐시 게이지 시각화
* **내용**: 플레이어 타임라인 진행 바에 현재 재생 위치(빨강/파랑) 외에 **다운로드 완료된 안전 버퍼 구간(연회색/반투명 흰색 바)**을 실시간 렌더링.
* **효과**: 사용자가 현재 네트워크 버퍼 상태를 직관적으로 파악할 수 있어 심리적 안정감 제공.

### 솔루션 3: 스마트 재생 재개 임계값 (Buffer Recovery Threshold)
* **내용**: 버퍼 부족으로 영상이 일시정지(스핀 로딩)되었을 때, 0.5초가 아니라 최소 **3초~5초 분량의 안전 버퍼가 확보될 때까지 대기 후 자동 재생 재개**.
* **효과**: 찔끔 재생 후 다시 멈추는 채터링 현상 완전 제거.

### 솔루션 4: 무손실 FastStart 메타데이터 최적화
* **내용**: MP4 컨테이너의 인덱스 메타데이터(`moov atom`)를 파일 맨 앞으로 이동 (`ffmpeg -i input.mp4 -c copy -movflags +faststart output.mp4`).
* **효과**: 재인코딩이 아니므로 **화질 손실 0%, 처리 시간 수 초 내외**. 첫 재생 및 탐색(Seek) 시 파일 전체를 스캔하지 않고 즉시 재생 시작.

---

## 4. Seek(구간 이동) 시의 동작 및 안정성 검증

1. **버퍼 내 구간 탐색 (Buffer Hit)**
   * 이미 선행 다운로드된 버퍼 범위(예: 10분~12분) 내로 이동할 경우 네트워크 요청 0건, **지연 시간 0.0초(즉각 재생)**.
2. **버퍼 외 원거리 점프 (Buffer Miss)**
   * 기존 진행 중인 다운로드를 즉시 중단(Abort)하여 대역폭 낭비 방지.
   * 백엔드로 새 위치의 HTTP Range 요청(`Range: bytes=xxx-`)을 발송하여 새 위치부터 즉각 버퍼링 재개.
   * `FastStart`가 적용되어 있으면 메타데이터가 메모리에 상주하므로 바이트 오프셋 계산 후 0.1~0.3초 내 데이터 수신.
